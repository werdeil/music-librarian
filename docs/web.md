# Dashboard

`watch --listen [HOST:]PORT` serves a dashboard on that address while it watches the Inbox: the passes running and the recent ones with their output, the schedule, the Inbox and the review questions awaiting an answer. The compose file serves it on port 8080 (`WEB_PORT` in `.env` to change the host's port); without a host, every interface is listened on. `MUSIC_LIBRARIAN_LISTEN` sets the address when `--listen` is not given.

The pages read the run history in the state folder and the Inbox root on each request. The passes the dashboard asks for are queued and run by `watch` itself, between its other jobs, so they never compete with them for the lock. When `watch` runs without `--apply`, a badge at the top says the dashboard is read-only. The footer gives the version. The overview ends on its environment, folded: the library, Inbox and state folders, whether passes are applied or previewed only, Lyrion's database, server (without its login) and automatic scan, the lyrics providers in their order, and the validated genre list with the iTunes lookup when `GENRE_LOOKUP` asks for it. While a pass runs or waits in the queue, a pill at the top of every page says so, refreshed every 5 s, and opens on a click onto the passes running, linked to their live output, and those queued.

A pass `watch` runs, from the dashboard or its schedule, can be stopped from its page or the pill: it ends the file it is on, as on `docker stop`, a tool of `enrich` included, then `watch` goes on with the rest of its queue; what the pass did is journaled, so it can be undone. A stopped scheduled pass runs again at its next slot. A request still queued can be cancelled from the history, the pill or its waiting page. A pass started by hand in another container cannot be stopped from here. Its spinner stays still when the system asks for reduced motion.

## Pages

- **Overview**: a **Checks** section, refreshed every 5 s, linking each count to where it is handled: the questions each review still awaits (as the Reviews page counts them), the imports left in `_failed/` (whatever the runs that sent them there were marked), the tracks with a field holding a value twice or several values. Each is a chip opening where it is handled. Those that need something come first, on a line of their own, tinted, their count before their name, the largest first; a count still being worked out gets a chip on that line after them, a spinner in place of its number; with neither, that line is left out. The tracks without lyrics count only those neither instrumental nor awaited, so their chip goes once each is sorted out; it opens the first album of the list of tracks without lyrics, and the chips of the inconsistent albums and of the years to fix the first of those, as their **Answer** on the Reviews page does. Then, on a line of their own, a ticked green chip for each count that is up to date, then grey ones marked – for each review switched off and for the genres when there is no validated genre list. The Discogs releases close to an album count only once a `physical` pass has read the collection. Then **Operations**: beside its title, **Add to the Inbox** (see below), **Download from Deezer** when it is set up, and **Run a pass…**. What the Inbox holds is not listed, `watch` reading it every 30 s; only a missing Inbox is told, in place of the first two buttons. Under them, the scheduled passes of `watch` (how often the Inbox is read, the nightly `organize`, the weekly `enrich` and, when `--physical-at` sets it, the weekly `physical`) with each command's last run and next slot, the whole row opening that run, and a link to the runs with problems of the last 7 days nobody has marked checked, when there are any. **Run a pass…** opens a dialog of the passes it can run: import, organize, enrich, scan and, with `DISCOGS_TOKEN` set, physical, each as a dry run first, its card opening a second dialog of its options (but import and physical, which have none); split, dedupe and the genres run from the Reviews page. The menu follows the overview's order (Overview, Reviews, Library, History, then Lyrion); its Reviews tab shows the total of the questions on every page, and a search box beside it opens the library searched for what is typed. On the library, the page's own search box takes its place and its look, beside the sort on a wider screen, in the header on a phone.
- **Failed imports**, linked from the overview: the items the import left in the Inbox's `_failed/`, hidden files aside, each with the reason the import run that sent it there gave and a link to that run, while it is among the 200 kept. **Retry** moves an item back to the Inbox's root, renamed `name (2)` when the name is taken there, where `watch` imports it again within a minute: fix its cause first, or it fails again. **Set aside** moves it to today's folder of `_done/`, which the import purges after `--keep-days`. Both change the Inbox at once, without a pass, and only when `watch` runs with `--apply`. An item belongs to the latest applied import run that sent it to `_failed/`: that run cannot be marked checked while one of its items is still there, its page saying how many, and is marked checked once the last of them is retried or set aside, whatever else the run reported.
- **Library**: the albums of the metadata cache, one per folder holding tracks, with their cover (`folder.jpg`, else the first embedded one, else a placeholder) and their number of tracks in its corner, under it their title and album artist, or *Compilation* for an album whose tracks all carry the compilation flag; or, under **Tracks**, a table of their tracks (album, number, title, artist), 100 per page. Both are searched by artist, album, title or folder without case or accents, a track kept when its folder, album artist, album, artist and title hold every word, as the words are typed (the results change in place and the address follows), and sorted by artist (the default), album, year (newest first) or by when a track was last added, removed or renamed in the folder, the tracks in their albums' order. Under the search box, **Advanced search** keeps the tracks by their fields, through conditions that must all hold, or at least one: a text field (any field, title, artist, album artist, album, composer, genre, grouping, folder, or any other tag by its name, such as `isrc`, an MP4 freeform tag or an MP3 `TXXX` one included) contains, does not contain, is, is not or starts with a value, is filled, is empty or has several values (several tags, or names separated by `;`); a number (year, track or disc number, duration in minutes) equals, is under, over or between values, is filled or empty; the lyrics (`[Instrumental]` counting as lyrics), the lyrics awaited, the embedded cover, the ReplayGain, a repeated value, the compilation flag and the physical mark (`PHYSICAL` in the comment) are there or not; the format (`m4a`, `mp3`, `flac`…) is or is not one. Text is compared without case or accents, and a condition missing its value is left out. An album shows when one of its tracks is kept, its corner then counting them (`3/12`); the track table adds a column for each field the conditions test. The filters above the results are searches of their own, a click putting their condition in the form, each with the albums, or the tracks, it keeps, and left out when it keeps none unless it is the one shown: the tracks without lyrics, those with repeated values, the compilations, those without composer, without genre, without embedded cover and without ReplayGain, and the physical ones. An album whose every track holds `PHYSICAL` shows a round disc in its cover's top right corner, named **Physical** on hover (see [physical.md](physical.md)). The switch between **Albums** and **Tracks** heads that line, then **All**, each filter with its count in brackets: the albums, or the tracks, the words of the search box keep; the number of results is written out only for conditions that no filter stands for. The address holds the whole search (`?c=composer:empty&c=year:between:1990:1999&match=any&view=tracks`), to bookmark it; the former `?only=lyrics` still opens its filter, and without script the form's rows are read as posted. A library never scanned shows nothing until a `scan`; a file moved or deleted since it was cached is left out. The list is built in the background as soon as `watch` starts serving the dashboard, then whenever the cache changes, so a page never waits on it: right after `watch` starts, it says it is still being worked out, under a bar of how far the build has read the cache, until the first build ends, and after a change it shows the previous list until the new one is ready; either way the page reloads by itself once the lists it shows are built, without waiting on the others (it asks `/built` every 2 s, and moves the bar), unless something was typed, ticked or unfolded on it meanwhile. The reviews and the lyrics page do the same. The lists are built one at a time, the album list first. While a pass writes the cache, the list is built again at most once a minute, and at once when the pass ends.
- **An album**: its number of tracks and their total duration under its title, its fields shared by every track (album artist, album, year, genre, number of discs, compilation flag) and a grid of its tracks (disc, number, title, artist, composer, grouping, the tracks of each disc under a row holding the disc's name, written to every track of the disc; the discs folded unless the album is numbered beyond one disc or holds a disc name, the grouping unless a track holds one, and a button shows what is folded), read from the files themselves, with each track's lyrics (present, instrumental, awaited, or none; a track without them neither instrumental nor awaited stands out as to sort out, its card unfolded on a phone, and opened from the list of tracks without lyrics, the lyrics of up to three such tracks start open), its ReplayGain track gain, its duration and its format, the file's name showing on hover. See below for editing them. Leaving the page with changes neither applied nor discarded (a field typed in, a cover picked, or a preview shown) asks first, in the browser's own words; **Preview the changes**, **Apply** and **Discard** do not. Each track's lyrics open on a page of their own, to edit or delete them, and the album's cover is replaced from its page, see below. A click on a track's gain strikes it out, a second click brings it back: the album form's **Preview the changes** then removes every `REPLAYGAIN_*` tag of the tracks struck out (the track gain and peak `enrich` writes, and any other a tagger left), with the other edits; the run's page shows each track's gain going, an applied pass is undone like any other, the tags written back as they were, and the next `enrich` measures the gain of those tracks again.
- **Repeated values**, linked from the library and the overview: the albums whose tracks have a field (title, artist, album artist, album, year, genre, composer) holding a value twice, a credit naming someone twice, or several values that differ, according to the metadata cache, the most such tracks first. The weekly `enrich` keeps once what is only repeated; what differs is fixed on the album's page, where those fields are outlined, their tooltip saying which case it is. The form refuses a title or an album holding a `;`.
- **Inconsistent albums**, linked from the reviews and the overview: the albums whose tracks disagree on an album field (album artist, album, year, genre, number of discs, compilation flag) according to the metadata cache, a track without a value counting as a value of its own, those differing on the most fields first. The genre is not counted when a track of the album carries the compilation flag. Each field is fixed on the album's page, which shows under it which tracks hold which value.
- **Years to fix**, linked from the reviews and the overview: the albums with a track without a year, or with a year that is not alone (`YYYY`), according to the metadata cache, those with both first. A track holds the year its edition came out, the one Apple Music and Lyrion show (see `dates.py`). The weekly `enrich` cuts a whole date down to its year; a year missing or unreadable is fixed on the album's page.
- **Tracks without lyrics**, linked from the library and the overview: the albums whose tracks carry no lyrics according to the metadata cache and are not sorted out yet, the most such tracks first. A track marked instrumental or awaited is left out, so the list empties once each is sorted out from its album's page; the number of tracks awaited is written above it, with a link to them in the library.

These three lists open on a line saying what they hold, their count and **Fix**, which opens the first album of the list; each album shows its cover, title and artist, and on its right how many of its tracks are concerned, or the fields its tracks disagree on.

An album opened from either list, or from a search of the library, keeps it: its page shows a bar with its position in the list, **Previous** and **Next** to the albums around it, and a link back to the list. The bar stays through a preview, an apply, an undo and a track's lyrics page. In the list of tracks without lyrics, which loops, **Later** stands in place of **Next**, which comes back once the album left the list: as soon as its page holds no track to sort out, before the album list is built again after a pass (the album then leaves the list and its counts at once, the Reviews page's included), and in place once the last of them is marked awaited, **Later** then only stepping on. Otherwise **Later** puts the album at the end of the list, after every album never put off, the one put off longest first, as the reviews' **Later** does (in `state/review-later.json`), and opens the album now standing where it stood, so the next visit starts with the albums not seen yet. Once fixed, an album leaves the list as soon as the album list is rebuilt; its page then counts the albums left and steps on from where it stood.
- **Lyrion**, shown when `LYRION_PERSIST_DB` is set: the play counts and ratings Lyrion keeps on files gone, and a button that starts its scan, see below.
- **Reviews**: the questions split and dedupe cannot settle, the genres the validated list does not know, the tracks without lyrics, the inconsistent albums and the years to fix, see below, and the files their answers are kept in.
- **History**: the passes the dashboard queued, at the top of the first page, then the runs kept in the history (the 200 latest, a running one included), 50 per page, filtered by command (each filter with its number of runs, the checkbox's included), and with a checkbox to the runs that failed, stopped, were interrupted or need checking and nobody has marked checked yet. A run's page marks it as checked or unmarks it, an import run only once the items it left in `_failed/` are retried or set aside (see Failed imports); a run marked checked shows a **Checked** badge, after its status when it failed, stopped or was interrupted and in place of **To check** otherwise, and leaves the problems of the overview and of the filter. A pass started by `watch` says why: at startup, for new items in the Inbox, as the day's import (which purges `_done/`), or on its schedule. The Inbox is read every 30 s, but an import runs, and shows in the history, only for one of those.
- **A run**: its mode, who started it (`watch`, the command line), for a pass started from a form of the overview the boxes that were ticked ("none" when none was), its duration and exit code, its summary, and its whole output, each line coloured by its tag (`ERROR`, `CONFLICT` and `FAILED` in red, `SKIPPED`, `WARNING`, `REFUSED`, `UNKNOWN`, `GUARDED`, `REVIEW`, `MULTIPLE`, `STOP` and `LOCKED` in yellow). While the run goes on, the new lines are appended every 2 seconds, and the page reloads with the summary once it ends. "Plain text" gives the output as a file.

Times are the container's (`TZ` in `.env`).

## Running a pass

The overview has a form per command: `import`, `organize` (`--since` ticked by default), `enrich` (`--rescan`, and the genres, the ReplayGain, the covers, the lyrics, the dates, the repeated values, the split and the aliases, ticked by default: unticking one passes `--no-genres`, `--no-replaygain`, `--no-covers`, `--no-lyrics`, `--no-repeats`, `--no-split` or `--no-dedupe`), `scan` (`--force`), `split` and `dedupe`. Their options are in the dialog the card opens, each box that makes the pass long (`--rescan`, unticking `--since`, `--force`) showing why while it is in that state; each card says that a preview comes first and nothing changes until it is applied (`scan` changes no file); **Preview** then queues the dry run and opens the run's page, which follows it live once `watch` gets to it; while a pass is running, the request waits in the queue, listed on the overview.

A run's page opens on the way back, above its title: to where the pass was started from when it was the album, the reviews or Lyrion, and **Back to the history**, to the history with the filters and page it was opened from. Once the pass ended, it leads with its outcome, its summary and what can be done next, the output folded underneath (open while the pass runs). The page of a dry run started from the dashboard offers **Apply this pass**: the same command with the same options, applied. It is a new pass, which plans again from the library as it then is. The page of an applied pass that left a journal offers **Undo this pass**, again as a dry run first. A pass queued from an album's page (its fields, a track's lyrics, its cover, the lookup of its lyrics) is followed on that page instead (see below), and its run's page offers **Back to the album**, where the pass filed it. Nothing is applied from the dashboard unless `watch` runs with `--apply`: without it, the dashboard runs dry runs only.

A request that finds the lock taken (a command run by hand, `docker compose run`) is not kept, and its page says so. The queue lives in `watch`: a restart drops the requests not yet started. The `--review` modes of `split` and `dedupe` ask questions and stay on the command line.

## Editing an album

Change any field on the album's page, then **Preview the changes**: the page comes back with the fields as typed and a box listing what a `tag` pass (see `music-librarian tag`) would do, one edit per field changed, an album field applying to every track: each change with its tracks, the folder the tracks move to, and what it would leave alone and why. The preview is a dry run worked out by the dashboard itself, at once, without waiting for a pass under way; nothing is written but the metadata cache. **Apply** then queues the pass applied, which writes the tags and files the tracks where their new tags put them, all in one journal; **Discard** shows the album as it is.

The album's page follows a pass queued from it, refreshed every 2 s: waiting in the queue (with **Cancel**), running (with its duration so far, its last line of output and **see the details**), then its outcome with its summary, **Undo** for an applied pass that left a journal (applied at once, itself undoable), and **see the details** for the run's page; a cross closes the panel once the pass ended, at once and without reloading the page. A dry run queued from it (a track's lyrics, the lookup of its lyrics) offers **Apply** in the same place. When the pass moved the album, the page goes to where it is now. A field left as shown is not rewritten, and an album field whose tracks differ shows "various values", left alone unless something is typed in. Under it, each value it holds, the most held first, with its tracks named when there are three at most, else counted: pointing at a value highlights its tracks in the table, and choosing it puts it in the field and keeps them highlighted (the empty value only highlights). The genre field offers the validated genres of `state/genres.txt`, and a genre the list knows takes its spelling.

Each edit carries the values the page showed: a track whose field changed in between, by another pass or another tagger, is refused (`REFUSED`) rather than overwritten.

On the album's cover, **Physical** shows as in the library when every track holds `PHYSICAL` in its comment, with how many do when only some do; **Look the edition up** shows the release its tracks name on Discogs. The next `physical` pass marks an album once its release is in the collection. See [physical.md](physical.md).

### Lyrics

A track's lyrics open under it from their cell of the album's page, in a text box that belongs to the album's form. They are edited, previewed and applied with the rest of the form: **Preview the changes** lists them by their number of lines (`1 line → 2 lines`), an emptied box removes them, and **Apply** writes them through `tag`, journaled, so **Undo** puts them back. Ticking **Instrumental** puts `[Instrumental]` in the box and locks it, the mark that keeps `enrich` from looking the track up; unticking it brings back the text it replaced. **Look up online** asks the providers (`LYRICS_PROVIDERS`) for that track only, at once, with the artist, title and album as typed in the form, applied or not (a blank field keeps the file's), and puts what they have in the box, or ticks **Instrumental**, saying where it came from or why nothing was found; nothing is written until the form is applied, and the lookup itself writes nothing. An edit made against lyrics that changed since is refused, as for any field.

A track without lyrics also offers **Not available yet, keep looking**, for lyrics no provider carries yet (a new release, a bootleg, a mashup): ticked or unticked, it is written at once to `state/lyrics-awaited.txt`, apart from the form and without a pass, one line per track naming what its lyrics are looked up with (`ARTIST — TITLE — ALBUM — M:SS`). An awaited track shows *awaited* in its cell and leaves the list of tracks without lyrics, but `enrich` still looks it up on every pass. Under the tracks, **Lyrics awaited for every track without lyrics** marks at once those of the album neither instrumental nor awaited yet, then, for an album opened from the list of tracks without lyrics, opens the next one. The mark is compared without case or accents and within 3 s, so it follows the track through a move; it is lost when its artist, title, album or duration changes, and dropped when lyrics or the instrumental mark are written. To change a line, edit the file.

### Edition

The year of an album is the year its edition came out, the one owned (see `dates.py`). **Look the edition up**, under the album's fields, shows the release an album's tracks name by their Discogs id (`DISCOGS_RELEASE_ID`, which `physical` writes), alone, asking no other provider; for any other album, it asks the providers of `EDITION_PROVIDERS` in turn (by default Discogs first once `DISCOGS_TOKEN` is set, MusicBrainz first otherwise) for the album's editions, the first that finds some answering, with the album artist and album typed in the form, and writes nothing: MusicBrainz (one request a second at most), Discogs (with `DISCOGS_TOKEN`, a year at most, no number of tracks), and iTunes (the store of `ITUNES_COUNTRY`, the album itself alone), whose date is often that of the digital release. Each gives the edition that the album's MusicBrainz id (MusicBrainz alone) or barcode names, else those of its artist and title. Each edition shows its year, its title linking to its page, its date, country, label and catalog number, number of tracks and format; those the id or barcode named come first, marked ✓, then those of the album's number of tracks, highlighted, then those of its very title, each kind the earliest first. With none found, the page tells nothing found by every provider from nothing found by those that answered, naming the others, and from no provider answering. **Take** puts an edition's year in the year field, previewed and applied with the rest of the form. `enrich` never looks an edition up.

### Cover

A click on the album's cover, at the top of its page, picks an image (32 MB at most) in any format ffmpeg reads (JPEG, PNG, WebP, GIF, BMP, HEIC…), shown in place of the cover at once; it is part of the album form, sent with its other changes. **Preview the changes** converts it to JPEG when it is not one and lists it with the sizes of the cover it replaces and of the new one, the page showing the new cover until the form is applied or discarded. Applied, it goes through the same `tag` pass as the other fields: the image becomes the album's `folder.jpg`, the previous one being kept in `covers/` in the state folder, it is embedded into the tracks, as `cover` does, then the album is filed again; **Undo** puts the previous `folder.jpg` back with the tags, which the next `enrich` embeds again. The image waits in `uploads/` in the state folder until then, removed after 7 days: an older preview can no longer be applied.

## Reviews

The Reviews page shows a card per review (the credits holding several names, the artists spelled several ways, the genres outside the validated list, the Discogs releases close to an album, the tracks without lyrics, the inconsistent albums, the years to fix), each with how many are left and what opens it: first those with something left, the largest count first, bordered and tinted orange, then those up to date, in green, then those not set up yet (the genres without a validated list, the Discogs albums before a `physical` pass has read the collection, whose button then reads it), then those switched off, both in plain grey, as their chips on the overview. Each card has a switch: a review switched off is left out of the menu's Reviews badge, and its chip on the overview, grey and marked – instead of ticked, shows no count, until it is switched on again; its card, greyed, still shows its count and opens its questions, and the passes still apply the answers already given. The switches are kept in `state/reviews-off.json`.

The reviews ask the questions of `split --review` and `dedupe --review` (see [splitting.md](splitting.md) and [dedupe.md](dedupe.md)) one at a time, in the same order and with the same suggestion, highlighted. Each page shows what the tags hold today, then one card per answer showing what it writes, and the page that follows an answer shows what it recorded the same way:

- a credit holding several names, as the tags hold it today (the field, the tracks, an album that carries it), then what each answer makes of it: **Split** into its fragments, a click on a separator joining the two on each side of it (`Emilio Estefan, Jr.`), **Keep whole**, or **Write these names**, typed separated by `;` from the split's names and shown as they will be written;
- a group of likely duplicates, each spelling with its number of tags and an album that carries it: the spelling to write them all as, picked among them or typed (typing it picks it), each other spelling shown with the one it becomes, or **Different artists**;
- a genre the validated list does not know, the one most tracks carry first, with its tracks and an album that carries it, each answer showing the genre it becomes: a name of a validated genre, added to its line of the list (the one iTunes suggests is picked, when `enrich.genres` looked the album up with `GENRE_LOOKUP=itunes`; without a suggestion none is, and the genre has to be chosen), or a validated genre of its own;
- a release of the Discogs collection only close to an album of the library (see [physical.md](physical.md)), from the collection the last `physical` pass kept, with its formats, year and page on Discogs, beside the album (a compilation as such): **Same album**, which the next pass marks, or **Another album**, never asked again; before any pass, the card says so and its button reads the collection;

**Later** puts the question at the end of its review, after every question never put off, the one put off longest first, as recorded in `state/review-later.json`, so the next visit starts with the questions not seen yet; the questions, and the albums of the list of tracks without lyrics, are numbered from the first one not put off in the round under way, so each **Later** moves the number on, back to 1 once every one was put off; the page that follows an answer offers to undo it. Each answer is written at once to `state/split-decisions.txt`, `state/artist-aliases.txt`, the genre list (`state/genres.txt`, or `MUSIC_LIBRARIAN_GENRES`) or `state/physical.json`, as in the terminal, so the review stops and resumes at will, and an answer that settles questions further down skips them. The queues are built from the metadata cache in the background, again whenever it changes, like the album list: until the first build ends, the counts and the questions say they are still being worked out, and the page reloads by itself once it ends. While a pass writes the cache, they are built again at most once a minute, and at once when the pass ends. Answers rewrite no tag: **Preview these answers**, on the Reviews page and under each question, queues `split`, `dedupe`, `enrich.genres` or `physical` over the library, whose page then offers to apply it and leads back to the reviews, or to the review it was asked from, and the weekly `enrich` applies them too.

The Reviews page also counts the albums holding tracks without lyrics neither instrumental nor awaited, and those tracks, in the menu's total too, which are not asked one at a time: **Answer** opens the first album of the list of tracks without lyrics, those put off with **Later** last, sorted out from its page and the next ones (see [Lyrics](#lyrics)), and **Lyrics awaited** the tracks of `state/lyrics-awaited.txt`, shown read only.

Each review links, from the Reviews page and under each question, to the file its answers are kept in, shown read only: the split decisions (each credit and what is done with it, the ones awaiting an answer included), the artist spellings (the variants rewritten as another name, and the artists known to differ), and the validated genres with the names that stand for each and the tracks of the library it gathers, so a genre no track carries any more stands out. To change a line, edit the file in the state folder; the next pass applies it.

## Lyrion

The **Lyrion** page holds three cards: the orphan play counts, writing to Lyrion, and Lyrion's scan. The first lists the orphans `playcounts` finds in `persist.db` (see [lyrion.md](lyrion.md#orphan-play-counts)), the most played first, 50 per page, under three lists: those **waiting** for an answer, counted beside the page's name at the top of every page and on a chip of the overview, those **settled** by an answer, a journal or their case, with the track that takes them or the mention that they are to delete, and those **ignored**. The page opens on the settled ones when none is waiting.

An orphan's page shows its play count, rating and last play, and the eight tracks of the library whose path looks most like its own, each with its note; the first is picked unless its note is under 60. A search box keeps the tracks whose path holds every word typed, when the right one is not among them. **Give to this track**, **Ignore** and **Delete** write the answer to `playcount-matches.json` at once and open the next orphan waiting, where the answer can be undone; **Later** opens the next one without an answer. Answering never writes to `persist.db`.

On the scan's card, **Start a scan** asks Lyrion at once for its scan of new and changed files, and says whether it started, Lyrion was already scanning or did not answer; it needs `LYRION_URL`. It moves nothing in the library, so it is offered whether `watch` applies its passes or not (see [lyrion.md](lyrion.md#asking-lyrion-for-a-scan)).

The card to write to Lyrion counts the settled orphans and queues `playcounts` as a dry run, with a box to copy the plugin's plays where Lyrion counts none (ticked) and one to compute the DPSV of every track again, each with the number of tracks it concerns. The dry run's page applies it, as for any pass.

The orphans are read from `persist.db`, opened read-only, in the background, again whenever it changes or a journal is written; the library is read from the metadata cache, again only when the cache changes, and its files are looked for on disk each time.

## Statuses

| Status | Meaning |
|---|---|
| Running | no end recorded yet, and its process is alive, or ran in another container (`docker compose run`) |
| OK | exit code 0 |
| To check | exit code 2: something was skipped, refused or failed; the output says what |
| Stopped | exit code 4: stopped before the end (`docker stop`, Ctrl-C), the rest is done by the next pass |
| Failed | any other exit code, such as 5 for a failed Lyrion carry-over |
| Interrupted | the pass crashed (its output ends with the traceback) or its process was killed, with no end recorded |

A pass whose process is gone is shown interrupted as soon as the dashboard sees it, when it ran in the same container; `watch` also marks the unfinished runs of its container as interrupted when it starts. A pass that found the lock taken is not kept in the history at all.

## Adding to the Inbox

**Add to the Inbox**, on the overview, sends music from the browser into the Inbox, where `watch` imports it as any copy: once it has settled, at its next read of the Inbox, within a minute. Folders and files are dropped on its dialog or picked with **Pick files** or **Pick a folder**; a folder keeps its name and subfolders (`CD1/`, `CD2/`) and becomes one item, a loose file an item of its own. Only the files the import takes are sent: the audio formats (those it turns down too, which then land in `_failed/`), images, booklets (`.pdf`), `.lrc` and `.cue`; the others, hidden files and `.DS_Store`, `Thumbs.db` or `desktop.ini` are left out and counted. Each file is sent on its own, 2 GB at most, with a bar of the progress; the dialog refuses to start when the disk lacks room for them all.

The files are written to a hidden folder of the Inbox, `.upload-<id>`, which `watch` does not read; once the last has arrived, each item is moved into the Inbox, named `Album (2)` when `Album` is already there. Cancelling, or a file that fails, removes the folder, so nothing is added; one left behind by a tab closed while sending is removed after 24 hours, the next time something is sent. While `watch` runs without `--apply`, the button is disabled.

## Downloading from Deezer

When `DEEZER_PRE_KEY` and `DEEZER_IV` are set (see [deezer.md](deezer.md)), the overview's Operations also offer **Download from Deezer**, a button beside **Add to the Inbox** whose dialog takes an album, by its deezer.com address or its id, or a playlist, by its address, queued as a `deezer` pass applied at once, whose run's page follows it; its tracks reach the Inbox once downloaded, and `watch` imports them. The button is disabled while `watch` runs without `--apply` or no arl is given.

The overview's environment then holds a Deezer line: where the arl comes from (the dashboard, `DEEZER_ARL` or none), whether Deezer refused it, whether the extension has its key, and a link to the **Deezer settings**. That page takes a new arl, checks it with Deezer (`deezer.getUserData`, the one request it makes) and keeps it in the state folder with its license token, in place of `DEEZER_ARL`; it also makes the Chrome extension's key, or a new one in its place. A missing or refused arl raises a Checks chip that opens the page.

The Chrome extension of `extensions/chrome` asks for a download through routes of its own, under `/deezer/ext/`. They answer 404 until a key is made on the Deezer settings, then only a request from a `chrome-extension://` origin, with CORS for it alone, and bearing `Authorization: Bearer <key>` (a preflight excepted). They need no page token, but the host name check applies to them as to every route, and they only queue a download and tell how far it has got. Each refusal answers JSON `{"error": …}` naming its reason.

## Languages

The pages are in French or English, after the browser's preferred language, English by default. The output of the passes stays in English.

## Security

The dashboard has **no authentication**: it is meant for a trusted home network. Anyone who can reach its port sees the library's paths, the names in the Inbox and the output of every pass, and can run any command, applied when `watch` runs with `--apply`, or add files to the Inbox, which `watch` then imports, or download into it from Deezer when that is configured. Each form carries a token of the page, and each file sent to the Inbox the same token in an `X-CSRF-Token` header, so another website open in a browser of the network cannot post to it. Nor can it read the pages through DNS rebinding, a name of its own pointed at the dashboard's address: the dashboard answers only to an IP address, a name without a dot (`nas`), a name under `.local`, `.lan`, `.home`, `.home.arpa` or `.internal`, and the names listed in `MUSIC_LIBRARIAN_WEB_HOSTS` (`watch --web-hosts`, comma-separated, e.g. `nas.example.org` or a Tailscale name); any other name gets a 403 that names the setting. Never expose the port to the Internet (no port forwarding, no public reverse proxy); for remote access, join the home network through a VPN such as WireGuard or Tailscale.

## For contributors

The package is `web/`: `app.py` (the overview, the header's activity and the app put together), `security.py` (the names it answers to, the forms' token and the response headers), `history.py` (the run history, a run's page and output, and the forms that queue, apply, cancel or stop a pass), `albums.py` (the library's pages and their forms), `common.py` (what the pages share: times, strings, a page of a list, a refusal, a queued pass), `passes.py` (the queue `watch` runs, how each command is built from the options of `watch`, and the uploaded covers), `library.py` (the albums and tracks from the cache, what a search finds, an album's fields, the edits of its form), `query.py` (the conditions of a search, read from its address, and the tracks they keep), `reviews.py` (the split, dedupe and genre reviews and their routes), `playcounts.py` (the Lyrion page and an orphan's), `uploads.py` (the files sent to the Inbox), `deezer.py` (the Deezer dialog and settings, and the extension's routes), `server.py` (waitress in a thread of `watch`, its request body raised to a file's 2 GB), `i18n/` (one module per language), `templates/` and `static/`. Flask is only imported with `--listen`.

- Every string shown lives in `web/i18n/`, in `fr.py` and `en.py` with the same keys; a test checks they match.
- Every response carries a `Server-Timing` header, which the browser's developer tools show beside the request: `total`, the time the app took, and for an album's page `files` (its tracks read), `list` (where it stands in its work list) and `reviews` (the questions counted for the menu). A wait much longer than `total` was spent before the app got the request.
- Under 640 px of width (a phone), the pages keep to the screen's width: the navigation takes a line of its own, the library search another under it, the album's tracks and the scheduled passes show as cards, each track's folded to its number and title behind a button that unfolds the rest (one holding a repeated value starts unfolded), a track's lyrics staying folded until asked for as on a wider screen, and the history leaves out the origin and duration columns.
- The Content Security Policy is `default-src 'self'; img-src 'self' blob:`: no inline script or style, everything from `static/`, but the image picked for an album's cover, shown from the browser before it is sent.
- The icons of the actions and of the overview's passes are symbols of `static/icons.svg`, drawn for the dashboard, placed by the `icon` macro of `_macros.html` beside a label they never replace, hidden from screen readers.
- The page scripts are plain JavaScript with no framework or build step, linted by `npx --yes eslint@9 src/music_librarian/web/static/*.js` (the CI lint job).
